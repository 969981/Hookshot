Date: 09. 11. 2026
  Features:
    - FSR 3 frame interpolation, and a jitter for the upscalers to undo.
    - The two backends have rows in the Insert menu.
    - Frame generation asks for its own extensions and the whole input set.
    - Link NGX properly, frame generation at the seam, AMD's interpolation sources.
    - DLSS at the seam, and a stage switch for the FSR cost.
    - A timed span per FSR pass, so the cost has a number per pass.
    - Count FSR evaluations, because nine passes a call is cheap or ruinous.
    - Compose the scene's view projection, and transpose it for the shader.
    - The hunt found the projection, so widen it to find the view.
    - DLSS Super Resolution through NGX, behind a build-time SDK gate.
    - RX_VK_VP_HUNT, to find the view projection from a value only it holds.
    - The vsync event follows the display, and 0 turns it off.
    - HOS_VSYNC_HZ, the hardcoded 60 that actually paces the game.
    - HOS_DISPLAY_VRR, which is what actually holds the frame rate at 60.
    - HOS_FPS_FORCE, because raising the limiter alone does not hold.
    - Give FSR the assembled depth and camera motion.
    - Derive camera motion from the scene's depth, and keep that depth.
    - Publish Ocarina's camera, and make a backend reachable without the stand-in.
    - Record FSR 3.1's nine dispatches.
    - Create FSR 3.1's pipelines and internal images.
    - Census the render target sets, to settle whether a G-buffer exists.
    - Compile AMD's FSR 3.1 upscaler passes from the FidelityFX SDK.
    - Route the game's upscale dispatch through one backend seam.
    - Name each network binding's role in the upscaler input contract.
  Bugfixes:
    - The conventionalcommits preset has to match the changelog writer.
    - The release's commit-analyzer preset is a package, and it was not declared.
    - A fork releases its own work, not upstream's.
    - The shader check compared glslang's version, and ran where glslang is not.
    - The DLSS contract test links again.
    - The renderer would not load, and the build now says so.
    - Scan for the view projection once a target set, not once a draw.
    - Clear the SPD counter between the pyramid passes (did not fix the cost).
    - The view projection scan ran per draw, which stuttered hard.
    - HOS_FPS_FORCE must not touch the nominal rate: it is slow motion on screen.
    - The host camera symbols must be weak, or the renderer does not load at all.
    - Snapshot the projection's fields, and name what caps the frame rate.
    - Publish the camera from the inlined projection copies too.
    - The game's network takes one texture, so it is not a temporal upscaler.
    - Read the upscaler contract in descriptor order, not from draw_sampled.

Version: 0.1.0
Date: 07. 11. 2026
  Major Features:
    - First release.
    - The game's AArch64 code is lifted to C and compiled natively on the player's PC from their own copy; no emulator is involved.
    - Horizon OS and NVN2 are implemented natively, and the GPU work is replayed on Vulkan.
    - Hookshot Builder on Windows and the Linux AppImage build the game without Visual Studio.
  Features:
    - Kokiri Forest: reaching gameplay and walking around.
    - Sound, controller, keyboard and saves.
    - In-game menu with frame generation and upscaling.
    - Movies, with a fallback when the PC has no AV1 decoder.
    - Linux: the AppImage carries the compiler, Python and the Vulkan back end; the built game runs without it.
  Changes:
    - Versioning starts at 0.1.0. Releases follow Semantic Versioning and semantic-release conventions; the changelog uses Factorio's format.
  Info:
    - Tested on one Windows PC (Ryzen 5 7600X, RTX 4060 Ti) and one Linux PC, mostly around the start of the game.
    - AMD and Intel graphics cards and the rest of the game are not tested yet.
    - A build needs about 60 GB free, and a run uses about 10 GB of RAM.
    - The repository contains no game files. The game is built from your own dump.
